# Koin — Overview

Dependency injection is **Koin Annotations + KSP**. The project does **not** use hand-written `module { single { ... } }` DSL for new feature/service modules — every implementation is annotated, and KSP generates the wiring at build time. The single production exception is `FeatureApiModule`, which composes cross-feature UseCases (each depending on multiple `*Feature` instances) and declares them inline with a `module { single { ... } }` block. That's a deliberate, documented carve-out, not a precedent for new modules.

## Why Koin Annotations

- **Multiplatform.** Hilt is Android-only.
- **Annotation-driven scaling.** Hand-written DSL doesn't scale to ~85 modules and ~85 singletons (verified: `grep -c '^include' settings.gradle.kts` returns 86; `grep -r '@Single\b' --include='*.kt'` returns ~60 plus 25 inline `single { … }` blocks inside `FeatureApiModule`).
- **Compile-time KSP.** No runtime reflection.
- **Cohesive API.** `@Module`, `@ComponentScan`, `@Single`, `@Factory`, `@Scoped`, `@InjectedParam`.

## The mental model

```
:shared/Koin.kt → KoinPlatformTools.defaultContext().startKoin {
    modules(
        ContextModule().module,
        BackendModule().module,
        DatabaseModule().module,
        // ... one per feature/area
    )
}
```

- Each `*Module` class is annotated `@Module @ComponentScan`.
- KSP scans the module's package for `@Single`, `@Factory`, `@Scoped` annotations.
- The `.module` extension is generated by KSP.
- Modules can `includes = [Other::class]` to compose; transitive includes are resolved automatically.

## Annotations

| Annotation | Meaning | Lifetime |
|---|---|---|
| `@Module` | Marks a class as a Koin module | per-compilation |
| `@ComponentScan` | Scan annotations in the module's package | per-compilation |
| `@Module(includes = [...])` | Compose other modules | resolved transitively |
| `@Single` | Singleton instance (one per Koin scope) | app lifetime |
| `@Factory` | New instance per `get()` call | per-resolution |
| `@Scoped` | Singleton within a custom scope | scope lifetime (rare) |
| `@InjectedParam` | Receive a parameter passed at `get()` time via `parametersOf(...)` | per-resolution |
| `@Single(binds = [Interface::class])` | Bind impl to interface | impl is registered under the interface type |

## What gets annotated

### Interface implementation

```kotlin
internal interface TrainingRepository { ... }

@Single(binds = [TrainingRepository::class])
internal class TrainingRepositoryImpl(
    private val api: GrippoApi,
    private val trainingDao: TrainingDao,
) : TrainingRepository { ... }
```

Note the singular/plural convention: the module is `TrainingsFeatureModule` (plural, named after the `:data-features:trainings` directory), but the interface/impl/feature classes are singular (`TrainingRepository`, `TrainingFeature`). Same pattern across other features: `ExerciseExampleRepository` in `:data-features:exercise-examples`, etc.

Consumers inject the interface: `private val repository: TrainingRepository by inject()` — or, more idiomatically in this project, via constructor.

### Concrete service (no interface)

```kotlin
@Single
public class GrippoApi internal constructor(private val client: BackendClient) { ... }
```

When the type is the only candidate, no interface needed.

### Factory (per-call instance)

```kotlin
@Factory(binds = [OperationManager::class])
internal class OperationManagerImpl(
    @InjectedParam val coroutineScope: CoroutineScope,
) : OperationManager { ... }
```

`@Factory` for stateful per-VM helpers. Each `BaseViewModel` calls `inject<OperationManager> { parametersOf(coroutineScope) }` and gets its own instance with its own scope.

### Module

```kotlin
@Module(includes = [BackendModule::class, DatabaseModule::class])
@ComponentScan
public class TrainingsFeatureModule
```

`@Module` declares the module; `@ComponentScan` enables KSP scanning. `includes` brings in dependencies' modules so a single `TrainingsFeatureModule().module` registration in `Koin.init` is enough.

## How a feature module looks

```
:data-features:trainings/src/commonMain/kotlin/com/<org>/<product>/data.features.trainings/
  TrainingsFeatureModule.kt            // public class, plural to match the module folder
  data/
    TrainingRepositoryImpl.kt          // @Single(binds = [TrainingRepository::class])
  domain/
    TrainingRepository.kt              // internal interface
    TrainingFeatureImpl.kt             // @Single(binds = [TrainingFeature::class])
```

`TrainingsFeatureModule.kt`:

```kotlin
@Module(includes = [BackendModule::class, DatabaseModule::class])
@ComponentScan
public class TrainingsFeatureModule
```

That's it. The module is empty — KSP scans the package for `@Single`/`@Factory`/`@Scoped` annotations and registers everything.

## How a service module looks (with explicit providers)

When a module needs to construct instances from a platform factory (`NativeContext.*`), a builder, or a Ktor/Coil/Json configuration block, it uses **inline provider methods** instead of separate annotated classes. `DatabaseModule` is the most prominent example — it provides the `Database` itself plus one method per DAO since Room generates the `Database` class but not per-DAO accessors:

```kotlin
@Module(includes = [ContextModule::class])
@ComponentScan
public class DatabaseModule {

    @Single
    internal fun provideDatabase(nativeContext: NativeContext): Database =
        nativeContext.getDatabaseBuilder()

    @Single internal fun provideTokenDao(db: Database): TokenDao = db.tokenDao()
    @Single internal fun provideUserDao(db: Database): UserDao = db.userDao()
    @Single internal fun provideTrainingDao(db: Database): TrainingDao = db.trainingDao()
    // ... one provider per DAO
}
```

The methods are `@Single` so Koin treats them as providers. Inside the method body, the actual instantiation logic runs.

The same shape is used by the toolkit/service modules that adapt `NativeContext` factory methods (`DataStoreModule`, `ConnectivityModule`, `LinkOpenerModule`, `NotificationManagerModule`, `PermissionManagerModule`) and the HTTP/JSON/image-loader stack (`HttpModule`, `SerializationModule`, `ImageLoaderModule`). Each declares its providers inline with `@Single internal fun ...` and lets `@ComponentScan` pick up any companion `@Single`-annotated classes in the package.

The platform auth modules (`GoogleAuthModule`, `AppleAuthModule`) follow the same inline-provider shape but **omit `@ComponentScan`** — they have no separate annotated classes in their package, only the single provider method. The `@Module(includes = [...])` declaration alone is enough; KSP picks up the inline `@Single` method directly. See `02-koin-annotations.md` for the "providers-only" carve-out.

## How `RootViewModel`, `RootComponent` consume Koin

Components fetch their VM's dependencies via `getKoin().get()`:

```kotlin
override val viewModel = componentContext.retainedInstance {
    ProfileBodyViewModel(
        dialogController = getKoin().get(),
        weightHistoryFeature = getKoin().get(),
        userFeature = getKoin().get(),
        updateWeightUseCase = getKoin().get(),
        stringProvider = getKoin().get(),
        notificationManager = getKoin().get(),
    )
}
```

Note `viewModel` has no explicit type annotation — `BaseComponent.viewModel` is `abstract val`, and the property type is inferred from the `retainedInstance { ... }` factory result.

ViewModels declare their constructor parameters explicitly; Koin resolves them via the `get()` calls inside `retainedInstance`. **Not** via direct injection annotations on the VM — VMs are not Koin-managed objects (they're managed by Decompose's `InstanceKeeper`).

## How `BaseViewModel` itself uses Koin

`BaseViewModel` implements `KoinComponent` and uses `by inject<...>()` for infrastructure deps:

```kotlin
public abstract class BaseViewModel<...>(...) : InstanceKeeper.Instance, KoinComponent {

    private val coroutineScope: CoroutineScope = CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)

    private val operationManager by inject<OperationManager> {
        parametersOf(coroutineScope)
    }

    private val errorProvider by inject<ErrorProvider>()
    // ...
}
```

Field injection is acceptable here because these are **infrastructure** deps shared by every VM. Feature deps (Features, UseCases, Controllers) come via the VM's constructor. `BaseComponent` uses the same pattern for `ResultManager` (`by inject<ResultManager> { parametersOf(coroutineScope) }`).

**Firebase is not Koin-managed.** `FirebaseProvider` is a `public object` (static singleton) initialized once per platform (`App.onCreate` on Android, `AppDelegate` on iOS). Anything that needs Crashlytics or Analytics — including `BaseViewModel.sendError` — calls `FirebaseProvider.recordException(...)` / `FirebaseProvider.logEvent(...)` directly. No `inject<FirebaseProvider>()`, no Koin module.

## What stays out of Koin

- **Composables.** Read tokens via `AppTokens.*`; read state via `viewModel.state.collectAsStateMultiplatform()`. No `koinInject` in screens.
- **Top-level extension functions** (mappers). Stateless; no DI needed.
- **Sealed class subtypes**. No annotations.
- **Routes, Directions, Loaders, Contracts.** Marker types; no DI.

## Anti-patterns

- **Hand-written `module { single { ... } }` DSL for new code.** Use annotations.
- **`@Single` on a stateful class without thinking through lifetime.** Singletons live for the app's life; their state survives all screens.
- **`@Factory` for stateless services.** Wasteful — `@Single` is correct.
- **Mixing constructor and field injection** in the same class. Pick one (constructor in production; field-injection only for `BaseViewModel`'s infrastructure deps).
- **Calling `getKoin().get()` in a Composable.** Wrong layer. Get deps via `Component → ViewModel`.
- **Forgetting to add a new module to `:shared/Koin.kt`.** The class won't be registered; `get()` fails at runtime with "no definition found".
